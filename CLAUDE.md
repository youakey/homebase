# CLAUDE.md — контекст проекта

## О проекте
Веб-приложение для совместного быта соседей по квартире: меню (завтрак/обед/ужин на неделю),
график дежурств по уборке кухни с обменами, объявления и чат, настройки профиля/проекта,
геймифицированная статистика. Мультитенантность через сущность "проект" (project_id).
Основная аудитория — мобильные пользователи, приоритет: скорость и простота UI.

## Стек
Vite + React + TypeScript (SPA, без Next.js) + React Router + Tailwind v4 + shadcn/ui
+ Supabase (Auth, Postgres, RLS, Realtime) + TanStack Query. Деплой: GitHub Pages
через GitHub Actions (статическая сборка, никакого своего сервера/API-роутов —
GitHub Pages их не выполнит, весь бэкенд — Supabase, вызывается прямо из браузера).

## Ключевые принципы
- Любые новые таблицы с данными проекта ОБЯЗАНЫ иметь project_id и RLS-политики,
  ограничивающие доступ approved-участниками этого проекта. Без RLS — не мёрджить.
  Это особенно критично здесь: anon key публичный (лежит в статическом бандле на GitHub Pages),
  вся защита данных — только на уровне RLS в БД.
- Все изменения схемы БД — только через файлы в supabase/migrations/, не через ручные правки в дашборде.
- Не использовать серверные фичи фреймворков (API routes, server actions, middleware) —
  билд должен оставаться полностью статическим для GitHub Pages. React Router используется
  в режиме чистого клиентского SPA (createBrowserRouter), без RSC/server actions/data-режима —
  это и требование хостинга, и обход известной уязвимости RSC Mode CSRF Bypass в react-router.
- UI — mobile-first: сначала вёрстать и тестировать на ширине ~375px, потом адаптировать на десктоп.
- Списки/ленты — с состоянием загрузки (skeleton) и пустым состоянием, без "голых" пустых экранов.
- Мутации, где это уместно (комментарии, блюда, чат, отметки), делать оптимистично через React Query.
- Секреты/ключи — не хранить в коде: локально `.env.local` (не коммитить), в CI — GitHub Actions secrets;
  переменные для клиента обязательно с префиксом VITE_.
- Имена людей в проекте — это profiles.full_name реальных пользователей, выбор ответственного —
  всегда через select из участников проекта, не через свободный текст.

## Структура (ориентир)
- src/pages/auth/... — вход/регистрация/онбординг (создать/вступить в проект)
- src/pages/menu/... — раздел Меню
- src/pages/cleaning/... — раздел Уборка
- src/pages/social/... — Объявления + Общение
- src/pages/settings/... — Настройки
- src/pages/stats/... — Статистика
- src/lib/supabase/ — клиент Supabase, типы БД
- supabase/migrations/ — SQL миграции
- .github/workflows/deploy.yml — автодеплой на GitHub Pages
- package.json `postbuild` — копирует dist/index.html в dist/404.html (SPA-фоллбэк для GitHub Pages)

## Текущий статус
Репозиторий: https://github.com/youakey/homebase (main). Supabase-проект подключён
(ref tfzyaeqfxqydmxzpglph, https://tfzyaeqfxqydmxzpglph.supabase.co), все миграции 0001–0008
применены и проверены (таблицы, RLS на всех таблицах, RPC-функции, views, storage-бакет avatars —
всё на месте). Секреты VITE_SUPABASE_URL/VITE_SUPABASE_ANON_KEY добавлены в GitHub Actions,
локальный .env.local заполнен реальными значениями. Деплой на GitHub Pages настроен и проходит
успешно (https://youakey.github.io/homebase/) уже с реальным бэкендом — проект полностью рабочий.

Реализовано полностью:
- Схема БД + RLS + RPC-функции (create_project/join_project/respond_duty_swap/cancel_duty_swap) +
  представления для статистики — supabase/migrations/0001–0008.
- Авторизация (email+пароль) и онбординг (создать/вступить в проект, pending/approved флоу).
- Базовый каркас: нижняя навигация из 5 вкладок, роутинг react-router (createBrowserRouter-стиль,
  чистый SPA-режим), переключение проектов.
- Раздел Меню: неделя × 3 приёма пищи, просмотр/редактирование, назначение ответственного,
  блюда, копирование прошлой недели с подтверждением перезаписи, комментарии (оптимистично).
- Раздел Уборка: неделя × 1 ответственный/день, отметка "выполнено", авто-статус "пропущено"
  (вычисляется на клиенте по дате, без cron/edge function), обмен дежурствами с обязательным
  подтверждением второй стороны (RPC respond_duty_swap/cancel_duty_swap).
- Объявления (закрепление, автор может удалить) + Общение (чат) в одной секции с табами,
  чат — через Supabase Realtime, пагинация "загрузить более ранние".
- Настройки: профиль (имя, аватар через Supabase Storage), инфо о проекте + инвайт-код,
  список участников, заявки на вступление (owner), переключатель проектов, выход, ссылка на
  входящие обмены дежурствами.
- Статистика: лучший повар / самый ответственный / самый активный в чате — через SQL views
  (security_invoker) на стороне Supabase, не агрегацией на клиенте.
- PWA (vite-plugin-pwa, манифест, иконки), 404-фоллбэк для SPA-роутинга на GitHub Pages,
  GitHub Actions workflow для автодеплоя.

Осталось:
- Живая проверка на реальном мобильном устройстве (регистрация → онбординг → меню/уборка/чат) —
  агент не может открыть браузер, нужна ручная проверка пользователем.
- Supabase Management access token, который пользователь дал для прогона миграций, стоит отозвать
  в Supabase (Account → Access Tokens) — он больше не нужен и даёт полный доступ к аккаунту.
- Заметка: у этого Supabase-проекта включена GitHub-интеграция (auto-deploy миграций при пуше
  в supabase/migrations/) — она уже подхватила 0001_init.sql самостоятельно при создании проекта.
  Значит новые миграции, добавленные через git push, могут применяться автоматически ещё раз —
  их нужно писать так, чтобы повторный прогон не ломался (идемпотентно), либо явно проверять
  в дашборде Supabase, что там всё ок, перед тем как полагаться на этот механизм.
